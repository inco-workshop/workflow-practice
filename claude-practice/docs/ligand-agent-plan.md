# Ligand Discovery Agent — 설계 플랜

> 상태: **플랜 (미구현)**. 이 문서는 "리간드 탐색"을 재사용 가능한 agent로 만들기 위한
> 설계안이며, 구현 전에 검토받기 위한 것이다. 구현은 별도 승인 후 진행한다.

---

## 0. 왜 agent로 만드는가

현재 리간드 탐색은 [03_ligand_landscape.md](../03_ligand_landscape.md)를 만들 때
사람이 그때그때 프롬프트로 지시해서 수행했다. 문제는 세 가지다.

1. **재현이 안 된다** — 같은 타겟을 다시 조사하면 검색어·순서·포함 기준이 달라진다.
2. **기준이 암묵적이다** — 어떤 화합물을 왜 포함/제외했는지가 대화에만 남는다.
3. **다른 타겟에 못 쓴다** — KRAS G12C용 대화를 다른 유전자에 복사하기 어렵다.

Agent로 만든다는 것은 **탐색 절차와 포함 기준, 출력 형식을 파일로 고정**한다는 뜻이다.
강의 4강의 "프롬프트가 아니라 환경을 설계한다"가 여기에 해당한다.

---

## 1. 범위 (Scope)

### 이 agent가 하는 일

**입력**: 타겟 지정 (유전자 + 변이, 예: `KRAS G12C`) — 선택적으로 기준 화합물

**출력**: 리간드 landscape 표 1개 + 근거 표 1개 + 탐색 로그 1개

### 이 agent가 하지 않는 일 (명시적으로 제외)

- 후보 **순위 매기기** — 이건 Phase 5의 일이고, 별도 기준이 필요하다
- 구조 **계산·도킹** — 별도 분석 단계
- "이 화합물이 좋다"는 **판단** — agent는 landscape를 만들 뿐이다

> 범위를 좁게 자르는 것이 핵심이다. 탐색과 판단을 한 agent에 넣으면
> "먼저 추천하고 근거를 찾는" 순서로 무너지기 쉽다 (CLAUDE.md §22).

## 2. 출력 계약 (Output Contract)

agent가 반드시 만들어야 하는 산출물을 먼저 고정한다. 이게 정해져야 절차를 설계할 수 있다.

### 2.1 `ligand_landscape.md` — 리간드 중심 뷰

| 컬럼 | 필수 | 비고 |
|---|---|---|
| Ligand | ✅ | 통용명 |
| Identifier | ✅ | ChEMBL ID / PubChem CID — **없으면 `Not found`** |
| Target | ✅ | 유전자 + 변이 |
| Binding mode | | covalent / non-covalent |
| Pocket | | switch-II 등 |
| Key residues | | 근거가 있을 때만 |
| Experimental structure | | PDB ID 또는 `None` |
| Activity | | 값 + 단위 + assay 종류 |
| Development status | ✅ | approved / clinical / preclinical / tool |
| Inclusion rationale | ✅ | **왜 포함했는지** |
| Evidence ID | ✅ | 아래 표와 연결 |

### 2.2 `ligand_evidence.md` — 근거 표

CLAUDE.md §10의 형식을 그대로 쓴다.

| ID | Claim | Evidence | Evidence Type | Source | Identifier | Confidence | Limitation |

### 2.3 `search_log.md` — 탐색 기록

재현을 위해 남긴다. 결과만 남기지 않는다 (CLAUDE.md §21).

- 사용한 DB와 버전/접근 일자
- 실제 질의어 전부 (성공·실패 모두)
- 반환 건수 → 포함 건수 → 제외 건수와 제외 사유
- 실패한 tool call과 원인

## 3. 탐색 절차 (고정된 단계)

각 단계는 **출력이 정해진 작업**이어야 한다. "잘 찾아봐"는 절차가 아니다.

### Step 1. 타겟 확정

- 유전자 심볼 → UniProt accession → 변이 표기 정규화
- **검증**: transcript / isoform / residue numbering이 일치하는가
- 실패 시 중단하고 사람에게 확인 요청

### Step 2. 구조 기반 열거

- RCSB PDB에서 해당 타겟의 구조 검색 → 각 구조의 결합 리간드 추출
- 용매·이온·뉴클레오타이드 제외 (`HOH`, `GDP`, `MG` 등)
- **산출**: PDB ID ↔ ligand code 목록

### Step 3. 활성 기반 열거

- ChEMBL에서 타겟에 대한 bioactivity 조회
- 활성값과 **assay 조건을 반드시 함께** 가져온다 (CLAUDE.md §7)
- **산출**: ChEMBL ID + 활성 + assay 메타데이터

### Step 4. 문헌·임상 기반 보강

- PubMed에서 타겟 + inhibitor 검색
- ClinicalTrials.gov에서 개발 단계 확인
- **산출**: PMID / NCT 번호

### Step 5. 중복 제거 및 통합

- 동일 화합물의 여러 이름(코드명 ↔ 일반명 ↔ 상품명) 병합
- 병합 근거를 기록 (임의 병합 금지)

### Step 6. 포함 / 제외 판정

아래 규칙을 **탐색 시작 전에** 고정한다.

**포함 조건** (하나 이상 충족):
- 해당 타겟과의 실험 구조가 존재한다
- 해당 타겟에 대한 정량 활성 데이터가 있다
- 임상/승인 단계이며 해당 타겟을 표적으로 명시한다

**제외 조건**:
- identifier를 확인할 수 없다
- 타겟이 다르거나 변이 특이성이 확인되지 않는다
- 검색 상위에 나왔다는 것 외에 근거가 없다 ← **가장 중요**

### Step 7. 산출물 작성

2절의 세 파일을 쓴다. 빈칸은 추측으로 채우지 않고 `Not found`로 둔다.

## 4. Agent가 지켜야 할 규칙

[CLAUDE.md](../CLAUDE.md)의 규칙을 상속하되, 탐색에 특히 중요한 것을 다시 명시한다.

1. **identifier 없는 화합물을 표에 올리지 않는다.** 이름만 아는 것은 `Not found`로 남긴다.
2. **존재하지 않는 ID를 만들지 않는다.** ChEMBL ID·PDB ID는 조회로 확인된 것만 쓴다.
3. **다른 assay의 수치를 나란히 비교하지 않는다.** 비교 불가하면 `Not directly comparable`.
4. **검색 결과 없음을 "존재하지 않음"으로 해석하지 않는다.** `Not found in <DB>, <date>`로 쓴다.
5. **순위를 매기지 않는다.** 범위 밖이다.

## 5. 패키징 방식 — 세 가지 선택지

| 방식 | 형태 | 장점 | 단점 |
|---|---|---|---|
| **A. Skill** | `.claude/skills/ligand-search/SKILL.md` | 절차와 출력 형식을 문서로 고정. Claude가 필요할 때 자동으로 불러 씀. 사람이 읽고 고치기 쉬움 | 컨텍스트를 본 대화와 공유해서, 검색 결과가 대화를 채움 |
| **B. Subagent** | `.claude/agents/ligand-search.md` | 탐색의 지저분한 중간 과정이 격리됨. 결과 표만 돌아옴 | 중간 판단을 사람이 볼 수 없음 → checkpoint 원칙과 충돌 |
| **C. Nextflow 파이프라인** | `main.nf` + 조회 스크립트 | 완전 재현. 버전·seed 고정. 폐쇄망 반입 가능 | 문헌 해석처럼 판단이 필요한 단계는 코드로 못 옮김 |

### 권장: A를 먼저, 필요해지면 C로

- **A (Skill)** 로 시작한다. 절차와 기준을 파일로 고정하는 것이 가장 큰 이득이고,
  탐색 과정을 사람이 볼 수 있어야 checkpoint가 작동한다.
- **B (Subagent)** 는 타겟을 여러 개 동시에 훑을 때만 고려한다. 지금은 불필요하다.
- **C (파이프라인)** 는 DB 조회처럼 **결정적인 부분만** 나중에 옮긴다.
  Step 2~4의 조회는 코드로 옮길 수 있고, Step 6의 판정은 사람/agent 몫으로 남는다.

## 6. 검증 계획 (구현 전에 정한다)

agent를 만들고 나서 "잘 되는 것 같다"로 끝내지 않기 위해, 평가 방법을 먼저 고정한다.

### 6.1 재현성 테스트

같은 입력(`KRAS G12C`)으로 **두 번 독립 실행** → 두 landscape를 비교한다.

- 포함된 화합물 집합이 같은가
- 다르다면 왜 다른가 (DB 업데이트 vs agent의 비일관성)

### 6.2 정답 대조 (KRAS G12C를 벤치마크로)

이미 사람이 만든 [03_ligand_landscape.md](../03_ligand_landscape.md)가 있다.
이것을 정답지로 쓴다.

| 지표 | 확인 내용 |
|---|---|
| Recall | 기존 표의 화합물을 agent가 찾아내는가 |
| Precision | agent가 추가한 것이 실제로 타당한가 |
| 환각 | 존재하지 않는 ChEMBL/PDB ID를 만들지 않았는가 ← **불합격 기준** |
| 근거 연결 | 표의 각 행이 evidence 표와 연결되는가 |

> 환각이 하나라도 있으면 다른 지표와 무관하게 불합격으로 본다.

### 6.3 이식성 테스트

KRAS가 아닌 다른 타겟(예: `EGFR T790M`) 하나로 돌려본다.
KRAS에만 맞춰진 하드코딩이 있는지 드러난다.

## 7. 폐쇄망 고려사항

현재 탐색은 전부 온라인 도구(BioMCP, ToolUniverse, 웹 API = **T3**)에 의존한다.
배포 파이프라인의 필수 경로에 두면 안 된다.

| 단계 | 현재 | 오프라인 대체 |
|---|---|---|
| 구조 열거 | RCSB REST API | PDB 로컬 미러 (T1) |
| 활성 조회 | ChEMBL API | ChEMBL dump (T1) |
| 문헌 | PubMed API | 확인 필요 |
| 임상 | ClinicalTrials.gov | 확인 필요 |

→ Skill 단계에서는 온라인으로 쓰되, **조회 결과를 로컬 캐시로 저장**해서
나중에 오프라인 재현이 가능하게 남긴다.

## 8. 미정 항목

정직하게 남겨둔다.

- **화합물 동일성 판정 기준** — InChIKey로 할지, 이름 매칭까지 허용할지 미정
- **문헌 검색 범위** — 몇 건까지 볼 것인지, 리뷰 논문을 포함할지 미정
- **활성 데이터 우선순위** — 같은 화합물에 여러 assay 값이 있을 때 무엇을 대표값으로 쓸지 미정
  (현재 방침: 대표값을 정하지 않고 전부 나열)
